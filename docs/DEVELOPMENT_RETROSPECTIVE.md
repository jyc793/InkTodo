# 墨待 InkTodo 开发复盘

复盘日期：2026-09-05。范围：从产品定义、分阶段实现、视觉迭代、手机和平板调试，到开源、正式签名、发布及安装。

依据：用户在本次对话中的反馈，项目 `MASTER_PROMPT.md`、`task_plan.md`、`progress.md`、`findings.md`、README、当前相关源码，以及本次对话中的构建和设备安装结果。本报告是经验总结，不是重新执行的全面质量审计；历史测试通过不等于当前所有设备与系统条件均已验证。

## 1. 总体结论

墨待最有价值的成果，是把一个界面极简、系统交互复杂、审美要求明确的产品做成了可独立运行和分发的 Android 应用。真正的难点集中在四处：后台提醒在系统约束下的可靠性、多个界面共享同一份任务状态、山水视觉与文字可读性的平衡、真实计时与流畅绘制的分离。

项目中最有效的做法是：把需求写入项目、持续编译、集中业务命令、使用非破坏性迁移、保留真实时间作为计时依据、依靠用户实机反馈校正实现、发布时核验最终下载文件。

最需要改进的地方是：过早用技术指标代表用户体验达标；对“自动弹框”“连续流动”等词缺少具体场景定义；视觉小改动曾扩大为布局和内容变化；早期缺少 Git 检查点；文档和验证状态未持续收敛；授权过程中没有足够早地识别工具能力边界。

## 2. 产品要求：长清单有价值，但必须转成可验收条目

用户一开始就限制了功能范围、技术方向、风格、优先级和禁止事项。这使产品没有变成带登录、云同步和复杂分类的通用待办工具，也让“提醒可靠性高于动效”成为实际取舍依据。

但保存原文只完成了第一步。对于每个重要需求，还需要四项内容：具体场景、可观察结果、失败条件、验证证据。

例如，“正式提醒强”不能只映射为 HIGH 通知。用户真正期望的是：正在使用其他页面时，到点自动出现可确认界面，播放系统通知音，确认后结束本次提醒。它应拆成解锁、锁屏、权限不足、静音或勿扰、蓝牙播放中的不同验收项。

“水墨流动”也不能只映射为存在动画代码。它需要约定：山体稳定；云雾在正常观看时间内可感知；循环交界不跳图；文字保持清楚；后台停止装饰动画。

用户后续否决实体琉璃、要求只调小组件背景时，最新明确决定应成为当前验收依据，历史原文作为演变记录保留。建议为高频修改项建立简短的“当前已确认规格”，避免在大量旧消息中来回推断。

## 3. 阶段执行：保留构建门禁，减少不必要等待

先基础工程、再数据与核心交互、再提醒和权限，最后深化视觉，这个顺序有效降低了同时调试多个系统的成本。后期用户授权合并阶段或连续完成时，应该连续执行，同时保留每阶段内部的构建门禁。

需要区分三个概念：阶段边界、验证边界、用户确认边界。一个阶段可以先完成并编译，再继续下阶段；只有涉及用户偏好、设备交互或新授权时才需要用户参与。

本次一些轮次反复运行完整联合构建，提供了保护，但单纯背景明度修改不必与数据库迁移采用完全相同的验证成本。更高效的分层是：

| 改动 | 首先验证 | 交付前验证 |
|---|---|---|
| 背景颜色、透明度、裁切 | 真实资源预览、资源编译、文字可读性 | 必要构建及目标尺寸确认 |
| 锦鲤绘制 | 同秒进度、暂停与归位、前台重绘 | 目标设备方向切换与动态观察 |
| 跨日期任务 | 区间边界、迁移、命令同步 | 数据库与提醒集成、用户场景验收 |
| 正式提醒与权限 | 触发、投递、展示、声音、确认分段验证 | 锁屏/解锁/后台/蓝牙组合验证 |
| 发布签名 | Release 构建、签名和对齐 | 上传后重新下载、摘要与版本核对 |

测试应围绕本次改动可能破坏的行为，不能仅为数量增加重复断言。

## 4. 架构：集中业务入口比增加层数更重要

单 app Module、清晰 package、手动 AppContainer、Room、DataStore、Repository 和独立提醒组件适合本项目。收益来自边界明确，而不是模块或抽象数量多。

`TaskCommandService` 是关键：完成任务既要更新数据库，也要取消相关提醒、清理快照并刷新 Widget。小组件后来新增完成按钮时，复用同一个命令入口避免了“桌面显示完成，但旧提醒仍然响”的旁路。

应继续坚持：Screen 展示状态并转交操作；ViewModel 组织页面状态；命令服务协调跨组件副作用；调度、通知、音效和恢复由各自组件负责。

“Single Activity”最后实际演化成主界面单 Activity，并为正式提醒和小组件确认提供独立 Activity。当前 Manifest 能证实这一点。经验是架构说明必须准确表达例外，不能 README 继续用一句 Single Activity 掩盖真实系统入口。

对于“先取消旧提醒，再保存或重排”的跨系统操作，单纯调用顺序不能保证数据库与 AlarmManager 的原子性。恢复快照、幂等命令和失败记录有实际价值；未来测试应覆盖中途失败与进程被终止的状态，不只覆盖顺利执行。

## 5. 跨日期任务：模型正确不等于全链路正确

跨日期持续任务曾出现提醒时间存在，但日历只显示开始日期的问题。这说明新增能力不能只检查编辑页与 Alarm。

完整影响范围包括：输入、校验、持久化、编辑回填、提醒计划、任务展示、日历墨点、日期列表、Widget 今日过滤、完成与恢复、重启恢复。

当前共享 `coversDate` 通过任务区间与自然日区间相交判断覆盖。采用 `[start, end)`：例如今天 14:00 到明天 00:00，不应把明天算作仍在进行的日期。日历只展开当前月，避免为一学期任务提前建立巨大日期列表。

本次特别核实：Room 2→3 迁移实际新增的是结束时间索引，起止 epoch 字段此前已存在。总结不能误写成“v3 才新增了完整开始和结束时间字段”。

可复用经验：同一个日期含义只实现一次；长区间按可见范围计算；旧数据升级通过真实旧 schema 验证，不使用删除数据库作为默认办法。

## 6. 提醒可靠性：必须观察完整链路

本次用户报告的“没有通知”“没有自动弹框”“没有声音”，表面相似，可能发生在完全不同的位置：

`任务保存 → Alarm 注册 → 系统触发 → Receiver 执行 → 通知提交 → 系统实际展示/发声 → 用户确认`

系统记录中存在通知，并不能证明用户看得到状态栏图标；通知渠道写了声音 URI，也不能证明蓝牙耳机实际播放了提示音；Activity 能从通知打开，也不能证明到点会自动弹出。

记录触发、投递、失败、取消与确认状态，比让用户反复开关权限更有诊断价值。诊断应显示真实阶段，不把“已提交给系统”写成“用户已收到”。

### 自动弹框的理解偏差

早期实现依赖 Full Screen Intent，并允许点击通知进入确认页，但这不等于用户要求的“正在使用手机时自动弹框”。后续使用获授权的 Overlay 处理解锁使用场景，锁屏保留独立确认入口。

这里的教训是先验证目标设备具体状态下的行为，再决定公开 API 组合。公开 API 的能力仍受系统版本、权限与厂商策略影响，不能承诺普通 App 在任意情况下具有系统自带应用的全部特权。

### 声音和蓝牙

历史检查没有证明墨待自己持有 Audio Focus 不释放。蓝牙静音的确切根因不能在复盘中被编造成已经完全定位。后续改为通知用途、非循环且有超时的声音路径，并避免系统闹钟与 App 正式提醒重复发声，这是减少干扰的工程措施。

可复用验收应同时看：提醒是否响、音乐是否恢复、确认是否立即停止相关音效、连续两个提醒是否互相干扰。声音可以只播一次，待确认状态持续保留；这两个生命周期要分开。

### 长持续提醒

日志记录了当时 Redmi 对通知附加约 72 小时 TTL 的观察，以及每 48 小时静默续期的实现。这个结果只应作为已观察设备的兼容策略，不能扩展成所有 Android 手机的固定规则。

跨学期支持不仅要求结束时间能存下来，也要求中间重启、通知恢复、续期和手动结束都能正确处理。模拟时间边界与真实多日观察是不同层次的证据。

## 7. 权限与通知渠道：可维护性必须面向用户

用户截图中的多条同名正式提醒，来自历次通知渠道版本遗留。代码不再引用旧 ID，系统设置也不会因此自动变得简洁。后续显式清理已知历史渠道并合并可复用的静默恢复职责，才改善了用户体验。

另外，正式渠道后期故意不承担声音，由独立有界播放路径负责。如果可靠性检测仍用“所有强渠道必须有声音”的统一条件，就会把正确配置误判成故障。

经验是：渠道应有稳定 ID、清楚职责和定向迁移；诊断判断必须与实际架构同步。绝不能为了让被用户静音的渠道重新响而不断更换 ID。迁移也要评估现存通知和用户设置，而非随意删光重建。

权限页应先告诉用户当前哪个功能受影响，只引导相关缺失项；返回页面自动刷新；已开启项目不反复提示。无法可靠查询的厂商项明确标为需要人工核对，不制造“全部正常”的假状态。

## 8. 水墨视觉：审美验收不能由像素统计代替

最初简化图形和普通半透明卡片没有达到用户要求的山水意境。真正推动质量提升的是用户参考图与录像，以及“静态背景好看，但动态不明显”“琉璃不好看”等具体反馈。

形成效果的关键是山峦前后层次、近深远浅、云海留白、青黛关系、山体稳定与雾层流动。几个颜色、圆角和渐变只能统一表面样式，不能自动产生空间氛围。

本次最明确的错误，是用 12 秒内大量像素变化证明动效达标。像素差只能说明渲染变化，不能说明人能感知连续流动。用户录像反馈后撤回验收结论是正确的纠正。

今后的动效验收应使用真实时长录像：正常速度看得见；循环接缝不跳；暂停和继续自然；背景不争夺阅读注意力。静态截图只验构图与可读性。

用户否决琉璃后，应保留其认可的山水母图，撤销被否决材质，不把最初名词当成必须强加的效果。统一主题的有效方式是共享视觉源和设计参数，再让山、月、水、雾各有局部特征。

## 9. 视觉修改的边界：只改背景就应只改背景

小组件调整中，用户想看一行文字和完整下半段风景的效果图，后来实现曾扩展为深色分支只显示一条任务和新布局方向，最终用户要求回退。

这里应承担的理解问题是：预览为展示风景暂时减少文字，不自动等于批准改变产品的任务容量。背景确认、预览样例、正式功能行为必须分别理解。

透明度也应明确对象：内容卡不透明度下降会让山水更明显，背景明暗调整却不应连带改变文字。用户说“深 15%”时，需要以指定基准图做可复现调整，而不是在亮度、饱和度、遮罩和字号之间同时修改。

最有效的流程是固定当前已认可的字体、按钮、布局和数据容量，只展示指定参数修改前后的同尺寸图，确认后修改对应资源。

## 10. Widget 和提醒浮层也是完整产品界面

主页、Compose 提醒 Activity、原生 View Overlay、RemoteViews Widget 的渲染和主题来源不同。主页开启深色模式，不会自动保证外部入口遵循 App 内的 DataStore 主题。

后续共享主题解析、显式设置 Widget 与 Overlay 配色、主题变化刷新 Widget，说明统一设计需要明确的数据传递与刷新机制，不能只靠同名 Theme。

Widget 的使命是桌面快速浏览。它可以沿用主页山水母图，但以静态背景、清晰文字和尺寸重排表达同一风格；不必复制主页动态云雾。用户要求深色模式的 Widget 更明亮，也完全可以作为受控的表面配色例外。

增加完成按钮时，首次点击进入确认、再次确认调用统一业务命令，是合理的误触保护。字体、行高、按钮触控空间、可显示行数必须一起核算；但只改背景时不应重新动这些参数。

## 11. 番茄钟：真实计时、文字刷新、运动绘制分开

平板出现每秒向前跳一段，来自锦鲤位置依赖每秒更新状态；之后横竖屏都冻结、旋转时瞬间归位，则暴露了通用动画开关关闭真实进度更新的问题。两个故障不能归因于“平板性能差”。

当前几何函数按持久化结束时间计算进度，运行时在可见页面逐帧更新；倒计时文字仍可按秒更新。暂停使用保存的剩余时间，重置与结束归位。

概念上有三条独立路径：

- 业务时钟决定真实剩余时间与系统结束提醒。
- 文字按秒呈现剩余时间。
- 绘制按帧采样同一时间依据，显示连续位置。

尾随水波属于装饰，系统减少动画时可以降级；锦鲤表达真实进度，即使降低运动强度，也必须保持信息更新，不能永久冻结。

墙上时钟可支持跨进程恢复，但会受用户改时间影响；单调时间适合当前开机周期内的时长。今后的计时规格应明确两者如何处理校时、重启和恢复，不能把使用逐帧回调等同于解决了所有时间问题。

完全专注中的六位 PIN 是自我约束交互，不是设备级锁定。勿扰模式也有独立的进入、退出、结束和异常恢复状态，需要与番茄钟共享时间事实，而不是由页面可见与否决定。

## 12. 测试证据：每句话对应一个实际验证层级

| 证据 | 可以说明 | 不能直接说明 |
|---|---|---|
| Kotlin/资源编译成功 | 该变体源码与资源可构建 | 提醒实际到达、视觉满意 |
| JVM 测试通过 | 所覆盖纯逻辑符合断言 | 厂商系统实际行为 |
| AndroidTest APK 编译成功 | 测试程序可构建 | 测试已经在设备执行 |
| 设备测试通过 | 指定设备与场景结果成立 | 所有品牌与系统都兼容 |
| 安装 Success | 系统接受该 APK | 全部历史任务数据完整 |
| 启动 Status: ok | Activity 成功启动 | 后台计时、声音、重启全通过 |
| 用户实测确认 | 被测试版本和场景可用 | 未测条件均无缺陷 |
| 下载摘要匹配 | 公布文件与核验文件一致 | 程序没有业务缺陷 |

最后手机安装中，firstInstallTime 与 lastUpdateTime 相同。执行过程确实没有卸载或清数据，但仅凭 `install -r` 成功，不能进一步证明此前全部业务数据保留。先前报告“原数据已保留”的表述应更谨慎；可靠证据还包括安装前后记录、签名与用户数据核对。

用户要求自己完成交互验证后，最有效的协作是提供短而准确的验收步骤：前置条件、操作、预期、异常时需报告的现象。自动化承担可重复逻辑与只读诊断，人负责真实感知和系统授权，不重复模拟用户点击。

## 13. Git、回退与长期记录

日志曾明确记录中期工程尚无 Git 元数据，直到开源准备才建立可见提交历史。这使视觉方向回退依赖文件记录和 APK 摘要，而不是明确提交，增加了时间和判断成本。

更好的做法是项目第一天初始化 Git，每个编译通过且可独立解释的修改形成小提交；已认可视觉建立检查点。用户说“回退到某一步之前”时，用检查点恢复指定范围，并保留后续无关修复。

记录应分成当前规格、验证状态、历史日志。当前计划部分增量阶段仍为 in_progress，README 同时包含已发布签名和“以后配置签名”的旧建议，也有对恢复渠道职责的旧描述。这些不是证明运行一定有错，但会让下一次维护错误理解项目现状。

本次不直接把旧阶段全部标成完成：需要先把每个版本和用户验收证据对齐。文件化记录提供了复盘依据，但冗长记录本身不是质量保证；必须定期整理出简明、准确的当前状态。

## 14. 开源与发布：认证、权限、产物是不同问题

本次 GitHub 授权经历多轮窗口与浏览器交互，用户反复看不到预期窗口。后来连接器更新文件返回 403，也说明“账号已连接”不等于该工具具有当前仓库写入与 Release 附件上传能力。

下次发布应先检查现有工具支持的动作、认证账户、目标仓库权限，再启动一次明确的授权流程；失败后根据状态换方法，不反复让用户等待同一个不可见窗口。日志必须脱敏。

正式发布成功的证据是完整的：专用证书、项目外签名配置、Release 收缩构建、签名/对齐校验、版本与标签核对、上传后匿名下载并核对摘要。

本次发布的 v0.1.0 为 3,484,251 字节，约 3.32 MiB，使用 v2/v3 签名。小体积说明静态优化素材与原生组件路线有效，但它不能独立证明低耗电或低内存，性能仍需单独测量。

长期更新必须保存同一签名材料，递增 versionCode，并归档版本、源代码提交、APK 摘要与验证设备。Debug 与正式版是否能覆盖，应检查签名，不能仅看文件名；同签名覆盖也不能替代数据库迁移验证。

显式导出/导入备份仍有后续价值，但属于待批准的产品增强；当前的 Room 无损迁移、安装不清数据与系统备份声明，不能等同于用户已拥有可恢复的外部备份。

## 15. 下一次可直接复用的工作流程

1. 固化核心目标、禁止事项和最新确认规格；为提醒与视觉定义具体场景。
2. 用短项目路径初始化 Git、构建工具、最小可运行工程和正式签名规划。
3. 优先验证最高风险能力：目标设备后台提醒、自动确认框、音频、Widget 与恢复。
4. 建立 Task 命令、时间区间规则和系统副作用入口，再铺开多个界面。
5. 用旧数据、时间边界和失败恢复验证模型；每次新增字段检查所有消费端。
6. 先确定一张有代表性的真实比例视觉稿，再推广主题；预览与正式布局授权分清。
7. 只调整用户指定范围；按风险定向测试，通过后再做交付构建。
8. 准备短实机验收单，记录设备、系统、版本、场景与结果；动效使用录像验证。
9. 每个稳定版本建立 Git 检查点，支持精确回退。
10. 发布时核验签名、版本、源码对应关系、下载摘要与干净构建配置。
11. 收尾时同步 README、当前规格和验证矩阵，保留未知项，不夸大完成范围。

## 16. 对本次协作的责任总结

用户持续提供真实场景、截图、录像、回退范围和使用感受，是产品从“可构建”走向“符合使用意图”的主要校验力量。要求先审计后修改、稳定代码只做局部变更、交互由用户验证，以及背景与字体分开调整，都有效减少了错误扩散。

助手应承担的改进责任包括：更早识别自然语言背后的交互条件；不把技术实现存在当作体验达标；不擅自扩展预览要求；不把音频线索包装为已确认根因；不反复发起无进展授权；精确表达安装、测试与数据保留证据；从第一天维护可回退的版本与简洁现状文档。

下次的效率提升，应主要来自更早验证高风险假设、更小且边界清楚的修改、更准确的证据与更少的返工，而不是一次生成更多代码。
